# Security policy

## Supported versions

Only the latest release receives fixes.

## Reporting a vulnerability

Please do not open a public issue. Use the private vulnerability reporting of this GitHub repository ("Security" tab, "Report a vulnerability"). You will get a first answer within 14 days.

## Scope

The stack is meant to run locally. The compose file binds the web service to `127.0.0.1` only. It has no user accounts and stores only public data. The API container is attached only to an internal Docker network that it shares with the web container, so it cannot open connections to the internet, and no container other than the web container can reach it.

The API allows each client address at most 16 data requests in progress, out of 64 for all clients together, and at most 2 of the 8 slots in which data queries run; its further requests wait for one of its own slots without holding a slot for large requests or a place in a shared queue. Its responses that are being built or waiting to be sent, cached ones included, may hold at most 50 MiB of the 100 MiB byte budget, so an address that requests large responses and does not read them cannot take the budget from the others. The client address is the one Caddy saw: the API takes it from `X-Forwarded-For` only on connections from the web container's fixed address, and a value that a client puts into that header itself is not used. `scripts/loadtest_abuse.py` reproduces the following on the `make prod-check` stack (21 November 2026). While one container held 100 parallel connections to `/forecasts/days` for 10 seconds, a second container requesting the forecast and seven days of three series without pause received 200 for all 212 of its requests in two runs, with a median of 91 and 97 ms. While one container kept 16 requests of 49,680 values each in flight, each for other days, the second container's forecast took 80 ms in the median instead of 11 ms without it; before the per-client query slots it took 2,062 ms (see [Architecture](docs/explanation/architecture.md#health-and-limits)).

Caddy closes a connection that has not sent its request header within 10 seconds and an idle keep-alive connection after 60 seconds. The web container may hold at most 4,096 open files, so Caddy accepts about 4,000 connections at a time and leaves further ones in the kernel's backlog; its memory limit of 256 MiB covers that number next to the compression of large responses. `make prod-check` opens 9,000 half-open connections from one container and fails unless the web container survives and answers again. Before these limits, about 7,000 such connections got the web container (then 128 MiB) killed for lack of memory. Caddy passes at most 192 connections to the API for data requests and 16 each for `/health` and `/status`, below uvicorn's limit of 256, so 400 connections from one client make the excess wait in Caddy instead of being refused, and `/health` and `/status` keep their own connections.

What this does not cover:

- The limit counts concurrent requests per source address, not requests per second. A client with many addresses gets one limit for each (IPv6 addresses count per /64 network), and users behind one NAT share one. All browsers on the host machine reach Caddy through the published port from the same Docker gateway address, so locally they share one limit.
- The two slots and the short queue for large requests, the connection limits of Caddy and the CPU limits of the containers still apply to all clients together, and two addresses holding their 50 MiB each fill the byte budget for unsent responses. A client within its 16 requests can keep the large-request slots busy, so other clients' requests for long periods wait or are refused. Four addresses with two query slots each can again fill all eight. A client that downloads large cached responses as fast as it can keeps the web container at its limit of two cores for compression; with `scripts/loadtest_abuse.py` on the `make prod-check` stack (21 November 2026) that raised other clients' forecast latency from 11 to 121 ms in the median.
- One client can still fill Caddy's 4,096 open files with half-open or idle connections. The container survives, but while the files are taken, new visitors wait in the backlog or time out, and some proxied requests fail with 502 (2 of 5,674 requests of `make loadtest` while `scripts/loadtest_abuse.py` opened 9,000 half-open connections twice, 21 November 2026).
- Behind another reverse proxy or load balancer, Caddy sees that proxy's address, and all clients share a single limit of 16 requests and 50 MiB. Such a proxy must set `X-Forwarded-For` to the client address, and its address must be trusted by Caddy (`trusted_proxies` in `docker/Caddyfile`) and by the API (`FORWARDED_ALLOW_IPS` in `compose.yaml`). Caddy then appends the proxy's address to the header, and the API counts the right-most address in it that it does not trust. A proxy on the host itself reaches Caddy from the gateway address of the `default` network, which Compose does not fix; give that network a fixed subnet before trusting the address.

Before exposing the stack beyond the local machine, put a reverse proxy in front of it that limits, per client address, the request rate and the number of concurrent connections, and closes connections that do not send a complete request header within a few seconds. A rate limit alone does not help against half-open connections, since they never become requests. Configure the proxy as in the last point.
